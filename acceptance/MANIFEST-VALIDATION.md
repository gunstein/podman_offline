## Resource-kind contract

The supported kinds are `Pod`, `ConfigMap`, `PersistentVolumeClaim` and
`Secret`. Empty YAML documents are ignored. Everything else is refused, with the
file and kind named: `Deployment`, `List`, a missing `kind` and a document that
is not a map. Names are checked after substitution. `references()` stays
recursive on purpose, because a link counts wherever it appears in a supported
document. The contract is documented in
[components](../docs/COMPONENTS.md#manifest-resource-kinds).

## Checks that need generated bytes

These run in `render.materialize`, after `generate_secrets`:

- missing or empty source files
- secret file names
- the Podman Secret size limit

For an existing database password, `database_preflight` checks that it is a
nonempty single-line regular file. Everything else is decided from declarations
before generation.

## How removal survives a retry

`apply_registration_updates` saves the owners of changed and removed
registrations in `pending-operation.json` before `write_registrations` writes or
deletes anything. A retry stages again. The registration is already gone, so it
produces no removal, but the pending owners are still carried over. Their
imports are rebuilt without the entry, and `acknowledge_owner` drops each owner
only after its restart and `is-active` check succeed. The record is cleared when
no owner remains. Absence never means removal for a component that is not being
installed.

## Understandability review

**Successful install, from CLI to durable state.**

1. `cli.main` calls `deploy.install`, then `install_components`.
2. Descriptors, pending conflicts, owners, dependency ranges and
   `install_needed` are checked.
3. `load_config`, `validate_component_config` and `check_public_settings` run.
4. `registration_stage` runs in a temporary directory and validates and returns
   imports, updates and removals.
5. `check_manifests` runs. It calls `effective_config` and `effective_documents`
   (pure), then `database_preflight`, which is the first host command.
6. `install_component_plan` then takes over:
   1. the image archive and image names are checked, then `materialize`
      (secrets, YAML)
   2. images are loaded and verified
   3. metadata
   4. `apply_registration_updates` (save the pending record, then write or
      delete)
   5. YAML, archives and Quadlet files
   6. owner imports
   7. restarts in `restart_order`, each acknowledged
   8. the completion marker last

Each step owns one kind of state, and the order puts every decision that needs
no side effect first.

**Failure and retry.** An owner restart fails after inventory's route was
deleted. The pending record already lists the gateway, so the retry stages
without the route (no new removal), carries the pending owner, rebuilds the
gateway import and restarts it. `acknowledge_owner` clears the record.

**One source of truth per decision:**

- supported kinds: `render.SUPPORTED_KINDS`
- pod traversal: `render.pod_specs`
- validation order: `deploy.check_manifests`
- what a release registers: its descriptor and role files, in
  `registration_stage`
- owner work: the pending record

**Simplifications made:**

- Six manifest traversals became one.
- The double render in install and `install_standalone` is gone.
- `uninstall_plan()` was extracted.
- The two restart and acknowledge loops became `restart_service()` and
  `acknowledge_owner()`.
- The 110-line preflight became four named functions.

**Remaining complexity:**

- Imported registration volumes appear in two forms: as names in
  `effective_documents`, taken from the descriptor's `accepts`, and as paths in
  `materialize`, taken from staging. Validation needs only the names, and the
  archive contents exist only once staging has run.
- The deploy and render modules grew by about 180 lines net. Most of that is
  documented helpers and the split preflight, not new mechanisms. The plan's
  expectation of "fewer lines" did not hold.
