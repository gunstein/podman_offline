# Unified file sources (0.4.6)

Backlog item 16 combines file delivery and optional one-time generation. All
component defaults and active examples use the same source-list schema:

```yaml
SECRET_FILES:
  app2-database-password:
  - path: credentials/database
    generate: [password]
  app2-signing:
  - path: credentials/todo
    generate: [session-key]
VOLUME_FILES:
  identity-clients:
  - path: ../clients
```

Each resource ID accepts one or more sources. `path` can refer to a prepared
file or directory. Optional `generate` lists filenames relative to a local
source directory; missing files are generated and delivered from that source.
Both groups support generation, although the current apps now deliver their
private files via Secrets after item 14. Prepared certificates/keys remain an
explicit external/script step. The directory/path-list format avoids duplicating
the credential path and retains multiple-source/file/directory support.

## Implementation and preserved behavior

- `deployment/render.py`: `file_group_sources()` validates resource IDs and
  source mappings (`path`, optional `generate`). Unknown fields, string-only
  source entries and malformed generation lists fail clearly. The old separate
  field is rejected, including during bundle source inspection; it is not
  ignored or converted. `generated_secret_paths()` resolves only explicitly
  selected files without generating or reading their contents.
- Generation validates the whole plan before creating any files. Targets stay
  beneath the config directory, rejecting absolute/tilde/traversing paths,
  symlink escapes, duplicate target declarations and file-as-directory sources.
  Creation still uses O_EXCL, 32 random alphanumeric characters, mode `0600`
  and private parents. Existing nonempty files are retained unchanged; empty
  or non-regular targets fail, as before.
- `deployment/deploy.py`: database preflight resolves password sources through
  the new mappings and still refuses a missing password with an existing
  database volume. A source with generate is explicitly a directory, even when
  its name equals the password key. Only `podman volume exists` status 1 means
  absent; other failures still refuse. No credential is generated by preflight.
- `bundle.py`: the guard follows all declared Secret sources and generated
  files in either delivery group, including aliases to arbitrary paths outside
  credentials/. General VOLUME_FILES content remains eligible for bundling;
  declared generated private files are excluded. Directory aliases and their
  descendants are covered, not just the credential directory-name filter.
- Component defaults, examples (including negative cases), current database
  acceptance helpers and unit fixtures use the new declarations. Internal
  generated-secret helper names remain because generation still creates secret
  files; there is no second config format or compatibility adapter.

The generation lifecycle boundary, top-level config precedence and authoritative
persistent config are unchanged. Database parameters, credential paths/bytes,
Secret/PVC names/keys, container mounts, component graph, retry persistence,
SELinux/fapolicyd policy, checksums and offline image behavior are unchanged.
The same generated value can be consumed by multiple declarations when only one
source declares generation. Repeating generation for the same target is rejected.
General volume archive normalization is unchanged; using generate does not turn
a VOLUME_FILES delivery into a Secret or change its runtime permissions.

All release version files are 0.4.6 because every bundle ships the new parser.
Application code, image tags and certificate issuance have not changed. There
is no migration, fallback, automatic config rewrite, credential move, deletion
or rotation. Fresh current config is initialized, then retained through ordinary
installs/upgrades/retries; no installed old-format config needs upgrading.

Local tests retain the existing rendering, database-preflight, init-config,
dev/state separation, preservation, fresh-process install/uninstall retry,
bundle/checksum, wrapper and offline/registry harness checks. New focused tests
cover generated volume imports/repeated bytes, mixed external binary and generated
sources, invalid mappings, source/target escapes, duplicate generation, a
file-as-directory source, obsolete-field rejection, same-name database directory
resolution, and private file/directory aliases outside credentials/.

All four negative example cases were also run through `examples/run.sh failures`
with a writable workspace TMPDIR: oversized Secret, partial placeholder, unknown
claim and unused ID each fail for their intended reason; cleanup passes. No
Podman is needed for these negative examples.

Historical verification reports/evidence and explicit 0.2.0 fixtures remain
unchanged, including `upgrade_020_guest.py` / `test_upgrade_020.py` and their
old config fields. Earlier BACKLOG task messages retain the original format as
history. Current docs mention the removed field only to explain its rejection.
Older results are not verification of the new schema.

Actual Podman/systemd installation, permissions, e2e authentication and
SELinux/fapolicyd behavior remain unverified in this workspace. No lab reset,
production state or real database volume was touched. The existing fresh
app1-first/app2-first and platform/help lab matrix remains applicable once
authorized; its preflight/runtime database checks now use the new declarations.
Python 3.6 compatibility is checked statically; no 3.6 interpreter or second
PyYAML version is available here. Stubbed harness tests do not prove container
runtime behavior.
