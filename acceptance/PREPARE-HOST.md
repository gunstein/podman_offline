## Mechanism and scope

`prepare-host.sh` keeps host-wide setup explicit. It checks that `/var/lib` is a
root-owned, non-symlink directory without group/other write permissions before
creating a service account. The existing account must have the declared home
and nologin shell, a nonzero UID/GID, and a real directory as its home. Root may
chmod that final home entry because the service user cannot replace its entry
in the trusted parent. Existing subordinate ID allocation and overlap checks
remain unchanged.

For all descendant preparation, `as_service_user` invokes RPM-provided `setpriv`
with numeric service UID/GID, cleared supplementary groups, empty inheritable,
ambient and bounding capability sets, and no-new-privileges. The helper CLI
also refuses effective UID 0. See the
[setpriv manual](https://man7.org/linux/man-pages/man1/setpriv.1.html) for these
flags. Real identity/capability state is asserted by the lab probe, not inferred
from seeing the command line in a mock.

The helper is embedded in `prepare-host.sh` as a quoted here-document and reaches
Python on stdin through a pipe, so the service user need not traverse a private
operator staging directory. It was first shipped as `scripts/prepare-home.py`, but
fapolicyd's default `%languages` rule denies every process opening an untrusted
Python file, and host preparation runs before any release is trusted (found in
lab run `h46b-platform`, see below). No new Python package,
PAM session, application import, generated bytecode or network access is needed.
The Python helper:

1. Opens the home and existing managed directory chain using `O_DIRECTORY` and
   `O_NOFOLLOW`, checks ownership through descriptors and checks the existing
   CNI lock without following it. A dangling link is an error, not absence.
2. Creates missing managed directories relative to held parent descriptors,
   reopens without following links and changes modes through `fchmod`. A path
   replacement cannot redirect that chmod to a different object.
3. Creates the lock using `O_CREAT | O_EXCL | O_NOFOLLOW`. If another process
   creates a lock first, it checks that object and leaves a valid regular lock
   untouched. It never unlinks, truncates or chmods an existing lock.
4. Closes all held descriptors even after a failed check or OS operation.

Both existing `restorecon` calls run through the same service-user boundary:
recursive home relabeling still excludes populated storage, followed by a
nonrecursive relabel of the storage directory itself. There is no root fallback.
This choice still requires OL9 confirmation that normal preparation works and
protected outside targets cannot be relabeled, including non-owned writable
files. A retained SELinux context alone is not proof of those properties.

Static checks reject links in the known directory chain and at the CNI lock;
they are not a blanket ban on links in application files. Dropping authority
does not create a filesystem sandbox: it does not promise that service-owned
outside files are inaccessible. Root checksum/trust/config-edit operations on
release trees remain item 54. Root must still execute trusted staged helper code.
No migration/compatibility layer or recursive ownership repair was added.

## Understandability and retry review

The authoritative inputs are the validated service account, root-controlled home
anchor and fixed list of rootless directories/lock. The generic helpers contain
no demo component, image, database, public URL or application-path assumptions.
Bundle copying already includes `scripts/`; the archive regression checks both
real helpers and their checksums. Platform export/isolation also copies both.

Successful flow: root validates host/account/ID ranges and SELinux equivalence,
then calls `prepare_service_home`. Its first unprivileged subprocess prepares
the directories/lock; two later unprivileged subprocesses relabel them. Only
after all succeed does root enable linger, update the firewall and print `[OK]`.
There is no new deployment state or completion record.

Failure/retry flow: a planted `.config/cni` link fails no-follow preparation.
The shell reports the unsafe home and stops before relabeling, linger or firewall
changes. A relabel failure similarly stops at that boundary. Earlier valid host
setup may remain; there is no rollback promise. An operator inspects/removes the
unsafe condition, then starts a new invocation. Existing credentials, regular
lock bytes/inode, subordinate IDs and container storage are retained. Ordinary
deploy/restart/uninstall state remains owned by the existing deployment engine.

The extra Python helper is limited to filesystem operations that need descriptor
binding and exclusive creation. The shell retains host command ordering and
privilege changes. No generic transaction framework or alternate config model
was introduced. The success/failure order and state ownership are explicit;
the understandability review is complete, while runtime verification remains open.

## Runnable real-host gates

`03-host-path-safety` runs the disposable proof as root on DEV, before any
product-specific branch. It creates a unique probe account and fixture home,
checks all UID/GID slots, supplementary groups, all capability sets,
no-new-privileges and the inherited SELinux context. It deliberately mislabels
owned config/storage directories, requires their default types after preparation,
and requires a labeled storage child to remain excluded. It tests fresh/repeated
preparation, normal/dangling directory and lock links, foreign ownership,
replacement before open and after open, and concurrent regular/link lock
creation. These injections execute the actual shipped helper bytes under the
service identity, not a duplicate implementation.

Disposable outside targets are root-owned, deliberately mislabeled fixtures;
some root-owned files are writable by the service user. The relabel tests plant
an intermediate `.local` link with an existing nested storage target and a final
storage link, then compare ownership, modes, bytes and labels. They inject at
the relabel command boundary; they do not instrument internal libselinux
directory walking. This is separate from the deterministic descriptor races.

`07-host-path-safety` on PROD temporarily plants CNI links as the actual service
user after normal installation, requires the full host script to refuse them,
restores the paths and repeats full preparation normally. It compares actual
container IDs, volume names/creation identities/mountpoint inodes and selected
storage/volume labels. `07-healthy-host-repeat` checks running consumers, followed
by the existing persistence/restart/reboot/upgrade scenarios. The renamed
product uses the same generic checks.

The ordinary flow explicitly uses the transferred `help` bundle for the PROD
probe, including the platform/help-only scenario. The renamed flow uses
`gateway`. Link fixtures share `planted_link`: cleanup covers the initial rename
and link creation as well as the probe body. A failure after rename restores the
original even when no link was created. If an unexpected non-link occupies the
original path, cleanup refuses to delete it and reports the retained backup path.
